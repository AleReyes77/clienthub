# ADR 0006: File uploads and storage

- **Status:** Accepted
- **Date:** 2026-11-21

## Context

Teams and clients need to share files on a project (briefs, designs, contracts). Uploads are one
of the most common sources of serious vulnerabilities: stored XSS, path traversal, malware and
denial of service.

## Decision

**Storage behind an interface** (`apps/api/src/lib/storage.ts`):

- S3-compatible object storage (AWS S3, Cloudflare R2, MinIO…) when `S3_BUCKET` is set.
- Local disk otherwise (development, single server).
- Both adapters pass the same contract tests; the S3 one runs in CI against S3Mock.

**Upload rules:**

1. Permission and project visibility are checked **before** the body is read.
2. One file per request, 10 MB by default (`MAX_UPLOAD_MB`), buffered in memory.
3. The type is detected from the file's **magic bytes**, never from the name or the browser's
   `Content-Type`. Only an allow-list is accepted (images, PDF, Office, ZIP, TXT/CSV/Markdown).
   **HTML and SVG are rejected**, because served from our origin they could run scripts.
4. The storage key is a random UUID generated by the server. The original name is sanitized and
   stored only for display.

**Download rules:** files are streamed through the API (after the same authorization checks)
with `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff` and
`Content-Security-Policy: sandbox`, so the browser never renders them in our origin.

**Deletion:** the database row is deleted first; the bytes are deleted by a background job.
Deleting a project also queues the deletion of all its files.

## Consequences

- Streaming downloads through the API costs API bandwidth. If that becomes a problem, switch to
  short-lived pre-signed URLs on a separate domain.
- No malware scanning yet (listed in the threat model as a known gap).
